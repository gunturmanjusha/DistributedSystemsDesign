01

Architecture framework

Requirements & Scope

Constrain the problem before selecting technologies.

Slack as a complete product spans many independently difficult systems. This study deliberately isolates the core messaging plane: accepting direct and channel messages, preserving conversation history, delivering to connected users, and recovering after temporary disconnection. Narrowing the boundary is an architectural decision, not a simplification of the workload.

The messaging plane already combines durable writes, near-real-time delivery, conversation ordering, persistent history, millions of long-lived connections, high-fan-out channels, and offline recovery. Search, calls, integrations, file internals, threads, reactions, and push notifications are excluded so those distributed-systems concerns can be analyzed without conflating them with adjacent storage and media pipelines.

Functional requirements

Functional requirements describe what the system must allow a user to do.

  • Send one-to-one and channel messages.
  • Belong to and communicate across multiple channels.
  • Retrieve persistent conversation and channel history.
  • Receive new messages in near real time while online.
  • Recover messages missed during a temporary disconnection.

Non-functional requirements

Non-functional requirements describe how well those capabilities must operate: low latency, durable acceptance, high availability, useful ordering, horizontal scalability, failure tolerance, and support for millions of long-lived connections.

Scope boundaries

Voice and video, full-text search, bots and integrations, file-storage internals, threads and reactions, and push-notification infrastructure remain outside the core design. They may consume messaging events later, but they should not distort the acceptance, history, delivery, and connection-management decisions being evaluated here.

Scale & Capacity

Establish the workload and its order of magnitude.

Capacity planning begins with explicit, hypothetical assumptions rather than claims about Slack production traffic. The goal is to establish an order of magnitude that can guide partitioning, throughput, connection management, and failure analysis.

Architecture framework · Design consideration

APIs & Data Model

Let access patterns and guarantees shape the contract.

The public contract and persistent model will be driven by the core access patterns: append a message, retrieve recent history, paginate backward through a conversation, validate conversation membership, and retain enough logical ordering information to detect gaps or resume after disconnection.

Endpoint schemas, identifier ownership, pagination cursors, storage technology, and the final history-partitioning key are intentionally not asserted here. Those choices depend on sequencing and reconnect semantics that must be made explicit first; publishing generic endpoints before those guarantees are defined would create false precision.

04

Architecture framework

High-Level Architecture

Separate durable acceptance from asynchronous delivery.

The architecture separates message acceptance from real-time delivery because they carry different guarantees. The synchronous path is deliberately short: User A passes through the load balancer to the Messaging Service, which validates the request and commits the message together with its outbox event. Only that durable commit is required before the sender receives an acknowledgement.

Delivery to recipients then proceeds asynchronously through the Outbox Publisher, Kafka, the Delivery Service, and the WebSocket Gateway. The sender does not wait for every recipient lookup, network push, or temporarily unavailable client. Persisting the message establishes the system-of-record state; the event stream then decouples delivery and future downstream processing from the synchronous write path.

If downstream delivery falls behind, the accepted message remains recoverable from authoritative history and the sender-facing request does not remain open. The trade-off is delayed delivery: durable buffering protects correctness, but consumer lag must be observed because it does not protect real-time latency.

Component responsibilities

Load Balancer
Distributes incoming requests and connections across healthy service instances. It owns no conversation history; health checks and connection distribution keep a single entry node from becoming the availability or throughput boundary.
Messaging Service
Authenticates and authorizes the sender, validates the request, assigns message metadata, and coordinates persistence. Durable conversation state remains outside process memory so service instances can scale horizontally and fail without becoming the source of truth.
Message Store
Owns authoritative conversation history and serves later history reads. Its partitioning, replication, and long-term growth model will determine whether the durable write path can sustain the target rate. Kafka does not replace this history responsibility.
Transactional Outbox
Stores the durable intent to publish beside the message in the same transaction. It closes the database/Kafka dual-write gap, while publication retries and an accumulating outbox backlog become explicit operational concerns.
Kafka
Buffers committed events and decouples downstream work from the write path. It owns a durable event log rather than the normal conversation-history API. Partition skew and consumer lag affect delivery latency even when acceptance remains healthy.
Delivery Service
Consumes accepted-message events and coordinates delivery to recipients. Recipient expansion, fan-out, retry, and backpressure belong on this asynchronous boundary rather than inside the sender’s synchronous request.
WebSocket Gateway
Owns live client connections and pushes real-time events. Capacity per gateway, connection routing, slow clients, gateway loss, and reconnection create a scaling problem distinct from message-write throughput.
Cache
May accelerate membership, conversation metadata, sessions, or connection-routing lookups. It is not authoritative for message history, and its exact contents and consistency policy depend on access paths still being refined.
05

Architecture framework

Critical End-to-End Flows

Treat acknowledgement as a durability contract.

Receiving a request is not the same as accepting a message. If the API returns success before persistence and then crashes, the sender has been promised a message that no longer exists. The acknowledgement boundary therefore sits after the authoritative database transaction: success means the system can recover the message even if the accepting service instance disappears immediately afterward.

If the sender receives a successful acknowledgement, the message has been durably accepted by the system.

The dual-write failure

A naïve implementation performs two independent writes—first inserting the message, then publishing MessageCreated to Kafka. Those operations are not one ordinary atomic transaction. If the database commits and the process crashes before publication, history contains the message while downstream delivery never receives the corresponding event.

Atomic persistence, asynchronous publication

The transactional outbox records both the message and its publication intent in the same database transaction. After commit, the sender can be acknowledged. A separate publisher reads committed outbox rows, publishes them to Kafka, and retries when Kafka or the publisher is temporarily unavailable. This moves publication retry off the user-facing critical path without losing the obligation to deliver.

The outbox does not make Kafka infallible. It makes the authoritative database state and the durable intent to publish consistent.

06

Architecture framework

Scaling Deep Dives

Examine connections, ordering, partitions, and hot-channel limits.

WebSockets create a stateful scaling dimension

Traditional HTTP request/response would require clients to poll for new messages, trading either frequent empty requests or higher delivery latency. A WebSocket begins with an HTTP handshake and becomes a long-lived bidirectional connection, allowing the gateway to push an accepted message to an already connected client.

At approximately 10 million concurrent users, this is not merely an HTTP requests-per-second problem. The gateway tier must collectively maintain millions of live sockets and their associated connection state. The tier can scale horizontally, but capacity per gateway, connection distribution, userId → gateway routing, slow-client backpressure, gateway failure, and controlled reconnection are separate design concerns that cannot be inferred from write throughput.

Order a conversation, not the entire system

Global ordering across every message would serialize unrelated conversations and sharply limit parallelism. The useful boundary is a logical conversation or channel: related events should retain partition-local order, while independent conversations should be free to progress concurrently.

Using conversationId as the Kafka key hashes every event for a conversation to the same physical partition. Millions of conversations do not require millions of partitions; many logical identifiers share a manageable set of physical partitions. This is an effective first partitioning strategy, but it also makes a single extreme conversation subject to the throughput ceiling of one partition and its assigned consumer.

Ordering where it matters; parallelism everywhere else.

Why more consumers do not fix one hot partition

A Kafka topic is physically partitioned, and each consumer group independently consumes that topic. Within one consumer group, a particular partition is assigned to one consumer at a time. Increasing consumer count improves parallelism only while partitions are available to distribute; it does not divide one hot partition among multiple consumers.

A hot conversation can outrun its partition

Consider a channel producing 50,000 messages per second while the assigned downstream consumer can process 20,000. The backlog grows by 30,000 records every second. End-to-end delivery latency rises continuously even if brokers, gateways, and unrelated partitions remain healthy.

The cluster may have unused capacity elsewhere, but partition affinity keeps this conversation constrained to one consumer within the group. Consumer lag becomes delivery lag, so the infrastructure can report healthy while messaging no longer feels real time.

Availability and real-time performance are different properties. A system can remain technically available while backlog growth makes the user experience operationally unacceptable.

Ordering pressure: strict conversation-wide ordering favors serialization.

Throughput pressure: extreme throughput favors parallelism.

The next design decision must reconcile useful conversation ordering with enough parallelism for an exceptionally hot channel. No final hot-channel strategy is claimed here.

07

Architecture framework

Consistency, Reliability & Failures

State every guarantee at its real boundary.

Durable acceptance

The strongest current guarantee is durable acceptance: a successful sender acknowledgement follows the authoritative message-and-outbox commit. This protects the write from an immediate Messaging Service crash and distinguishes acceptance from eventual recipient delivery. The Message Store remains the source for history; Kafka transports committed events and absorbs temporary downstream interruption.

Ordering boundary

Conversation-key partitioning supplies ordering within a Kafka partition, not a complete user-visible sequencing model. Concurrent senders, retries, duplicate events, replay, missing sequence detection, and reconnect behavior still require explicit semantics. Partition affinity is therefore a useful transport property rather than a claim that conversational ordering is fully solved.

Dual-write recovery

The outbox preserves the obligation to publish after the message commit. Messaging Service failure after commit is recoverable because durable state exists. Kafka or publisher interruption may delay delivery, but the committed outbox record retains the work for retry and makes the backlog observable.

Delivery semantics still to be defined

The outbox does not by itself provide exactly-once client delivery. Gateway failure affects live sockets and requires reconnection and missed-message recovery behavior; retries may also duplicate work. Client-visible delivery semantics, idempotency, replay, and slow-consumer handling remain explicit design considerations rather than implied guarantees.

08

Architecture framework · Further evolution

10×/100×, Multi-Region & Trade-offs

Stress-test saturation, centralized state, guarantees, and regional boundaries.

Scaling is not a multiplication exercise applied only to message writes. The architecture must be stress-tested component by component to identify the first saturated resource, the state that remains centralized, and the partition key that concentrates load. Storage throughput, Kafka partition skew, connection routing, reconnect bursts, and fan-out amplification can become limiting at very different points.

At extreme scale, the design must also test whether its guarantees remain affordable. Multi-region routing and failover introduce latency, replication, ordering, and consistency boundaries that cannot be resolved by capacity arithmetic alone. The next evolution will make those trade-offs explicit before assigning a 10× or 100× architecture.

Stress-test questions

  • Which component saturates first, and what resource sets that ceiling?
  • What state remains centralized, and which partition key becomes hot?
  • Does storage, Kafka, connection routing, reconnect traffic, or fan-out become the limiting resource?
  • Which ordering, delivery, or availability guarantees become unaffordable at extreme scale?
  • How do multi-region routing, replication, failover, ordering, and consistency interact?

A reusable design lens

  1. What problem does the component solve?
  2. What state does it own?
  3. How is that state partitioned?
  4. What becomes the bottleneck at 10× or 100×?
  5. What happens when it fails?
