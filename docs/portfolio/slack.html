01

Requirements & Scope

Constrain the problem before selecting technologies

Slack as a complete product spans many independently difficult systems. This study deliberately isolates the core messaging plane: accepting direct and channel messages, preserving conversation history, delivering to connected users, and recovering after temporary disconnection. Narrowing the boundary is an architectural decision, not a simplification of the workload.

The messaging plane already combines durable writes, near-real-time delivery, conversation ordering, persistent history, millions of long-lived connections, high-fan-out channels, and offline recovery. Search, calls, integrations, file internals, threads, reactions, and push notifications are excluded so those distributed-systems concerns can be analyzed without conflating them with adjacent storage and media pipelines.

Functional requirements define what users can do: send a direct message, post to a channel, retrieve history, and receive messages after reconnecting. Non-functional requirements define how well the system must do it: low latency, durable acceptance, high availability, useful ordering, horizontal scalability, and failure tolerance at millions of concurrent connections.

Kafka, caching, WebSocket gateways, replication, load balancing, partitioning, and transactional outbox are implementation mechanisms. They become relevant only after a requirement establishes the problem each mechanism must solve.

Scale & Capacity

Establish the order of magnitude

Capacity planning begins with explicit, hypothetical assumptions rather than claims about Slack production traffic. At 50 million daily active users and 100 messages per active user per day, the system receives 50M × 100 = 5B messages/day. Dividing by 86,400 seconds gives approximately 58K message writes/sec on average.

An illustrative 5× peak raises that to approximately 290K writes/sec. The working design target rounds upward to roughly 500K writes/sec for initial headroom. These figures establish the order of magnitude for partitioning and throughput analysis; message size, bandwidth, storage growth, replication cost, reconnect bursts, and delivery amplification require separate models.

APIs & Data Model

Let access patterns shape the contract

Design consideration

The public contract and persistent model will be driven by a small set of core access patterns: append a message, retrieve recent history, paginate backward through a conversation, validate conversation membership, and retain enough logical ordering information to detect gaps or resume after disconnection.

Endpoint schemas, identifier ownership, pagination cursors, storage technology, and the final history-partitioning key are not asserted here. Those choices depend on sequencing and reconnect semantics that must be made explicit first; publishing generic endpoints before those guarantees are defined would create false precision.

Design consideration

The contract must align online delivery with durable history.

04

High-Level Architecture

Durable acceptance, decoupled delivery

The architecture separates message acceptance from real-time delivery because they carry different guarantees. The synchronous path is deliberately short: User A passes through the load balancer to the Messaging Service, which validates the request and commits the message together with its outbox event. Only that durable commit is required before the sender receives an acknowledgement.

Delivery to recipients then proceeds asynchronously through the Outbox Publisher, Kafka, the Delivery Service, and the WebSocket Gateway. The sender does not wait for every recipient lookup, network push, or temporarily unavailable client. This keeps downstream latency and partial failures out of the acceptance path while preserving the accepted message in the authoritative history.

Kafka provides a durable handoff between the committed write and independently scalable delivery workers. If delivery falls behind, the message is not lost and the sender-facing write path does not have to remain open; the operational consequence is consumer lag, which must be monitored because durable buffering protects correctness but does not guarantee real-time latency.

01

Load Balancer

Sync · edge

Spreads incoming requests and connections across healthy instances. It owns no message history; health checks and connection distribution prevent one service node from becoming the entry-point bottleneck.

02

Messaging Service

Sync · control

Authenticates, authorizes, validates, assigns message metadata, and coordinates persistence. It remains horizontally scalable by keeping durable conversation state in the store rather than process memory.

03

Message Store

Sync · authority

Owns durable conversation history and serves later history reads. Its partitioning, replication, and long-term growth model will determine whether the authoritative write path can sustain the target rate.

04

Transactional Outbox

Sync · bridge

Stores the durable intent to publish beside the message in one transaction. It closes the database/Kafka dual-write gap, while the publisher and outbox backlog become explicit retry and observability concerns.

05

Kafka

Async · transport

Buffers accepted events and decouples downstream work from the write path. It owns an event log, not the normal conversation-history API; partition skew and consumer lag directly affect delivery latency.

06

Delivery Service

Async · dispatch

Consumes accepted-message events and will coordinate recipient delivery. Recipient expansion, fan-out, retry, and backpressure are its central scaling boundaries rather than responsibilities hidden in the synchronous API.

07

WebSocket Gateway

Async · connections

Owns live network connections and pushes events to connected clients. Gateway capacity, connection routing, slow clients, node failure, and reconnect behavior form a distinct connection-management problem.

08

Cache

Auxiliary · optional

May accelerate membership, metadata, session, or connection-routing lookups. It is not authoritative for message history, and its exact contents and consistency policy depend on the access paths still being refined.

05

Critical End-to-End Flows

Acknowledgement is a durability contract

Receiving a request is not the same as accepting a message. If the API returns success before persistence and then crashes, the sender has been promised a message that no longer exists. The acknowledgement boundary therefore sits after the authoritative database transaction: success means the system can recover the message even if the accepting service instance disappears immediately afterward.

A naïve implementation performs two independent writes—first inserting the message, then publishing MessageCreated to Kafka. Those operations are not one ordinary atomic transaction. If the database commits and the process crashes before publication, history contains the message while downstream delivery never receives the corresponding event.

The transactional outbox records both the message and its publication intent in the same database transaction. After commit, the sender can be acknowledged. A separate publisher reads committed outbox rows, publishes them to Kafka, and retries when Kafka or the publisher is temporarily unavailable. This moves publication retry off the user-facing critical path without losing the obligation to deliver.

Scaling Deep Dives

Connections, ordering, and the hot-channel limit

Connection architecture

WebSockets create a stateful scaling dimension

Traditional HTTP request/response would require clients to poll for new messages, trading either frequent empty requests or higher delivery latency. A WebSocket begins with an HTTP handshake and becomes a long-lived bidirectional connection, allowing the gateway to push an accepted message to an already connected client.

At approximately 10 million concurrent users, this is not merely an HTTP requests-per-second problem. The gateway tier must collectively maintain millions of live sockets and their associated connection state. The tier scales horizontally, but capacity per gateway, connection distribution, userId → gateway routing, slow-client backpressure, gateway failure, and controlled reconnection are separate design concerns that cannot be inferred from write throughput.

Ordering boundary

Order a conversation, not the entire system

Global ordering across every message would serialize unrelated conversations and sharply limit parallelism. The useful boundary is a logical conversation or channel: related events should retain partition-local order, while independent conversations should be free to progress concurrently.

Using conversationId as the Kafka key hashes every event for a conversation to the same physical partition. Millions of conversations do not require millions of partitions; many logical identifiers share a manageable set of physical partitions. This is an effective first partitioning strategy, but it also makes a single extreme conversation subject to the throughput ceiling of one partition and its assigned consumer.

A topic is physically partitioned, and each consumer group independently consumes those partitions. Within one consumer group, a particular partition is assigned to one consumer at a time. Adding consumers increases parallelism only while partitions are available to distribute; it does not divide the work of one hot partition among multiple consumers.

Throughput boundary

A hot conversation can outrun its partition

Consider a channel producing 50,000 messages per second while the assigned downstream consumer can process 20,000. The backlog grows by 30,000 records every second: 300,000 are waiting after ten seconds and 1.8 million after one minute. End-to-end delivery latency rises continuously even if brokers, gateways, and unrelated partitions remain healthy.

The cluster may have unused capacity elsewhere, but partition affinity keeps this conversation constrained to one consumer within the group. Adding more consumers does not automatically parallelize that partition. The design has therefore reached a genuine trade-off: one conversation key simplifies ordering, while extreme channel throughput requires additional parallelism.

07

Consistency, Reliability & Failures

State each guarantee at its real boundary

The strongest current guarantee is durable acceptance: a successful sender acknowledgement follows the authoritative message-and-outbox commit. This protects the write from an immediate service crash and distinguishes acceptance from eventual recipient delivery. The Message Store remains the source for history; Kafka transports committed events and absorbs temporary downstream interruption.

Conversation-key partitioning supplies ordering within a Kafka partition, not a complete user-visible sequencing model. Concurrent senders, retries, duplicate events, replay, and missing sequence detection still require explicit semantics. Similarly, the outbox preserves publication intent but does not by itself provide exactly-once delivery to a client.

Failure analysis must therefore follow state ownership. Messaging Service failure after commit is recoverable because durable state exists. Kafka or publisher interruption can delay delivery while the outbox retains work. Gateway failure affects live connections and requires reconnection and missed-message recovery behavior. Those connection and delivery semantics remain design considerations rather than implied guarantees.

10×/100×, Multi-Region & Trade-offs

Scale Evolution — To Be Stress-Tested

Further evolution

Scaling is not a multiplication exercise applied only to message writes. The architecture must be stress-tested component by component to identify the first saturated resource, the state that remains centralized, and the partition key that concentrates load. Storage throughput, Kafka partition skew, connection routing, reconnect bursts, and fan-out amplification can become limiting at very different points.

At extreme scale, the design must also test whether its guarantees remain affordable. Multi-region routing and failover introduce latency, replication, ordering, and consistency boundaries that cannot be resolved by capacity arithmetic alone. The next evolution will make those trade-offs explicit before assigning a 10× or 100× architecture.

SAT

Which component saturates first?

Evaluate storage, Kafka, connection routing, and fan-out independently.

HOT
