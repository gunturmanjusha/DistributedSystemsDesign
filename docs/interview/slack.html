Section 1

Requirements & Scope

Freeze the behavioral contract, workload assumptions, and system guarantees before selecting technologies.

What We Are Solving

We are designing the core real-time messaging subsystem of a Slack/WhatsApp-style platform—not the entire product. The system must support direct and channel messaging, durable history, near-real-time delivery to connected users, temporary disconnection and recovery, millions of persistent connections, concurrent desktop/browser/mobile sessions, and synchronization of state such as read position across devices.

The point of this phase is to make the contract explicit. By its end, we should know the scope, workload assumptions, latency and availability targets, durability invariant, ordering boundary, cross-device consistency model, and baseline fault-tolerance expectation.

Question to ask the interviewer

Are we designing the entire Slack/WhatsApp product or only the core messaging subsystem?

Decision: focus on the core messaging subsystem.

In Scope

  • One-to-one direct messaging
  • Channel/group messaging and membership
  • Sending and receiving messages
  • Persistent history and history retrieval
  • Near-real-time online delivery
  • Disconnect, reconnect, and missed-message recovery
  • Multiple active devices per user
  • Cross-device read/unread synchronization

Out of Scope

  • Voice and video calling
  • Full-text search
  • Bots and integrations
  • File-storage internals
  • Threads and reactions
  • Push-notification infrastructure

These can be independent subsystems or future extensions. Excluding them keeps the interview centered on acceptance, persistence, ordering, partitioning, fan-out, connection management, reconnect, and recovery.

Functional vs Non-Functional vs Architecture Decisions

This distinction prevents premature technology selection. A capability such as synchronizing read state is functional; the decision that read state may temporarily diverge but must converge quickly is a consistency requirement; the storage and event mechanisms used to achieve that are architecture decisions.

CategoryQuestion it answersExamples
FunctionalWhat does the system do?Send a channel message; retrieve history; recover messages missed offline; synchronize read state.
Non-functionalHow well must it behave?Latency, availability, durability, ordering, consistency, scalability, and fault tolerance.
Architecture decisionHow will we satisfy the requirement?Kafka, WebSockets, replication, partitioning, transactional outbox, and caching.
Requirement↓Constraint↓Architecture problem↓Design choice↓Trade-off

Example: the requirement that acknowledged messages must not be lost creates a consistency problem between durable database persistence and downstream event publication. A transactional outbox is a possible design response. The mechanism follows the requirement; it is not the starting point.

Senior-level rule

Do not begin requirements gathering with “I would use Kafka, Redis, and WebSockets.” First establish the problem each mechanism must solve.

Ask how many users are active daily, how many messages each active user sends, and how many users may be connected simultaneously. When the interviewer does not supply values, state assumptions clearly.

Do not perform the full capacity calculation during requirements gathering. These values become inputs to Section 2 — Scale & Capacity, where we derive write QPS, delivery QPS, bandwidth, storage growth, replication overhead, gateway capacity, reconnect bursts, and 10×/100× pressure points.

The fan-out path may be significantly more expensive than the write path. Section 1 freezes that observation; detailed calculation belongs in Section 2 and fan-out architecture belongs in Section 6 — Scaling Deep Dives.

Latency Requirements

Question to ask: What does “real time” mean for this system? Do not reduce latency to one number. Sender acknowledgement and recipient delivery traverse different boundaries and should have separate SLOs.

Sender ACK latencyClient sends → durable acceptance → sender success

Determines how responsive sending feels.

Online delivery latencyMessage accepted → delivery pipeline → connected recipient

Measures the asynchronous real-time experience.

What I Should Know — p50, p95, and p99

Average latency can hide a poor tail. Percentiles describe the distribution and make the slowest user experiences visible.

MetricMeaningWhy it matters
p5050% complete at or below this latency.Median or typical experience.
p9595% complete at or below it; 5% are slower.Common service-level view of a meaningful tail.
p9999% complete at or below it; 1% are slower.Exposes severe tail behavior that averages conceal.
Illustrative interview design assumptions
Sender ACK: p95 < 200–300 msOnline recipient delivery: p95 < 500 msOnline recipient delivery: p99 < 1 second

These are explicit working assumptions, not universal Slack or industry standards. Replace them when the interviewer supplies requirements.

A sub-second target does not follow automatically from availability. If 50,000 events/sec arrive while consumers process 20,000/sec, the service can remain up while backlog grows by 30,000/sec and delivery becomes minutes late. Availability does not imply acceptable latency. The hot-partition and consumer-lag analysis continues in Section 6.

Availability Requirements

Question to ask: What availability level should the core messaging service provide? Assume high availability: failure of one Messaging Service instance, gateway, Kafka broker/consumer, cache node, or storage replica should not collapse the entire messaging system.

An availability SLO measures the proportion of valid service requests successfully served over a measurement window. Values such as 99.9%, 99.95%, and 99.99% represent different error budgets and operational investments; there is no universal target for every messaging system.

Illustrative interview design assumption

Use approximately 99.99% availability for the core messaging path only if the interviewer requires a number and provides none.

PropertyQuestionImplication
AvailabilityCan the service successfully handle valid requests now?Depends on redundancy, failover, and operational health.
DurabilityWill previously accepted data survive failures?Depends on the acknowledgement boundary and replicated persistence.
Critical distinction

99.99% availability does not mean losing 0.01% of messages is acceptable. Availability and durability are independent guarantees.

Durability Requirements

Critical question to ask: Once the sender receives a successful acknowledgement, may the system permanently lose that message? For this design, the answer is no.

If the sender receives a successful acknowledgement, the message has been durably accepted by the system.
Unsafe acknowledgement1. Client sends M100 2. Messaging Service receives M100 3. Service returns SUCCESS 4. Process crashes before persistence 5. M100 no longer exists

The service made a promise it cannot keep.

Required semantics are conceptually receive → durably persist → acknowledge. The precise store and outbox mechanics belong in Section 4 — High-Level Architecture and Section 5 — Critical Flows.

Exact Sender ACK Boundary

For this design, the sender receives a successful ACK only after the authoritative database transaction containing both the message and its outbox event commits successfully.

The sender does not wait for Outbox Publisher → Kafka publication → Delivery Service → WebSocket push → recipient delivery → recipient read. Sender ACK means durable server acceptance, not recipient delivery. This keeps the synchronous write path short while delivery continues asynchronously.

If Kafka is temporarily unavailable after commit, the ACK remains valid: the authoritative message is durable, the atomically committed outbox record preserves the publication obligation, and the Outbox Publisher can retry later. Database persistence without the corresponding outbox intent is not sufficient for this design. Detailed outbox mechanics remain in Sections 4 and 5.

Do Not Confuse Acceptance, Delivery, and Read

StateMeaning
Accepted / Sender ACKThe server has durably accepted the message.
DeliveredThe message has reached a recipient client/device according to delivery semantics defined later.
ReadThe recipient has opened or advanced past the message and read state has been recorded.
Accepted ≠ Delivered ≠ Read

Section 1 establishes only that these states are different. Delivery receipts, exactly-once delivery, read receipts, and per-device acknowledgement mechanisms belong primarily in Sections 3, 5, and 7.

“Kafka must be 100% available” is the wrong requirement: Kafka may be temporarily unavailable while authoritative acceptance remains safe. “100% durability” is also not a useful absolute claim across every imaginable correlated disaster. State the actual guarantee instead:

Frozen durability requirement

The design targets zero acknowledged-message loss within its defined failure model.

The baseline model includes process, machine, individual broker, and individual storage-node failures. Regional disaster and correlated replica loss require Section 8 decisions.

Failure Model and Fault Domains

The baseline guarantee covers independent component failures. Correlated fault-domain failures have a wider blast radius and require replication topology and failover decisions that are intentionally deferred.

Failure categoryExamplesDesign scope
Independent component failureProcess failure; application-instance failure; machine/node failure; individual Kafka broker failure; individual storage-node/replica failure.Covered by the baseline failure model.
Correlated fault-domain failureAvailability-zone failure; regional failure; correlated replica loss.Requires explicit replication topology, failover, and multi-region decisions in Section 8.
Failure-model principle

A durability guarantee is meaningful only when the failure model it is designed to survive is stated explicitly.

Ordering Requirements

Question to ask: Is ordering required globally, per user, or per conversation/channel? Global Slack-wide ordering provides little user value and forces coordination between unrelated conversations.

Channel AA1 → A2 → A3
Channel BB1 → B2 → B3

No useful requirement establishes whether A2 globally preceded B2.

Preserve meaningful ordering within a logical conversation or channel—not globally.

Within conversation C123, infrastructure should not arbitrarily expose M1, M3, M2 when the messages have an established order. Unrelated conversations should progress independently: ordering where ordering matters; parallelism everywhere else.

Section 1 defines the boundary, not the implementation. Simultaneous senders, sequence assignment, retries, duplicates, gaps, hot channels, and cross-partition behavior are deferred to Sections 3, 6, and 7.

Multi-Device Consistency

Question to ask: If the same account is active on desktop and mobile, how consistent must state be across devices? Separate durable message history from mutable user metadata.

StateRequired behaviorConsistency decision
Message historyAll devices converge on the same accepted conversation history.Authoritative durable data; a message cannot permanently exist for one device but not another.
Read/unread positionA read on one device propagates to other sessions.Fast eventual consistency; brief divergence is acceptable, indefinite divergence is not.

Synchronous coordination with every device before updating the desktop UI would add cost without matching the low business impact of a briefly stale unread badge. A likely representation is a per-user/per-conversation read cursor, but that is a Section 3 — APIs & Data Model decision rather than a frozen schema here.

Scalability and Fault-Tolerance Requirements

The architecture must scale horizontally across tens of millions of active users, billions of daily messages, millions of persistent connections, uneven conversation activity, very large channels, and high delivery fan-out. It cannot assume one server, broker, partition, or database node handles the workload.

The baseline failure contract is equally direct: failure of an individual component must not permanently lose an acknowledged message or collapse the entire messaging service. Service, database, Kafka, consumer, gateway, cache, network, duplicate-processing, retry-storm, offline-client, reconnect-storm, and backpressure behavior are tested in Section 7 — Consistency, Reliability & Failures.

One-Line Interview Answers

What are we designing?
The core real-time messaging subsystem: DMs, channels, durable history, online delivery, reconnect recovery, and multi-device synchronization.
Functional vs non-functional?
Functional requirements describe behavior; non-functional requirements define qualities and guarantees.
Requirement vs architecture decision?
A requirement states the capability or guarantee; Kafka, WebSockets, caching, and partitioning are mechanisms selected to satisfy it.
What scale are we assuming?
Approximately 50M DAU, 100 messages per active user per day, and 10M peak concurrent connections.
What does real time mean?
A normally sub-second connected-user experience, with sender ACK and recipient delivery measured separately.
What are p95 and p99?
p95 includes 95% of operations and p99 includes 99%; they expose tail latency that an average can hide.
Availability vs durability?
Availability asks whether requests can be served now; durability asks whether accepted data survives failures.
Does 99.99% availability permit message loss?
No. Availability and message durability are independent guarantees.
When exactly do we ACK the sender?
After the authoritative transaction containing the message and outbox event commits successfully; we do not wait for Kafka publication or recipient delivery.
Does sender ACK mean the recipient received the message?
No. Sender ACK means durable server acceptance; delivery and read are separate later states.
Accepted vs delivered vs read?
Accepted means durably stored by the system, delivered means it reached the recipient client under our delivery semantics, and read means recipient read state was recorded.
Do we promise absolute 100% durability?
No; we target zero acknowledged-message loss within an explicitly defined failure model.
Why do we define a failure model?
Because durability can only be evaluated against the failures the architecture explicitly claims to survive.
Independent failure vs fault-domain failure?
A node or broker failure is an independent component failure; availability-zone or regional loss is a correlated fault-domain failure requiring additional replication and failover design.
Do we need global ordering?
No. We need meaningful ordering within a conversation or channel while unrelated conversations scale independently.
How should read state behave across devices?
Brief divergence is acceptable; authoritative read position should propagate and converge quickly.
Message history vs read state?
History is authoritative durable data; read state is metadata that can use fast eventual consistency.
Why can fan-out dominate ingestion?
One stored channel message can create thousands or hundreds of thousands of recipient-delivery operations.
Baseline fault-tolerance requirement?
One component failure must not permanently lose an acknowledged message or take down the entire service.
What I Would Say in the Interview

“I would scope this to the core real-time messaging subsystem rather than the complete Slack product. I need direct and channel messaging, durable history, near-real-time delivery to connected users, reconnect recovery, and multi-device synchronization. I would initially exclude calls, search, file-storage internals, integrations, threads, reactions, and push notifications.

Unless you give me different scale, I’ll assume roughly 50 million daily active users, 100 messages per active user per day, and 10 million concurrent connections. I’ll distinguish sender acknowledgement from recipient delivery and target a sub-second online experience, looking at p95 and p99 rather than averages alone.

The service should be highly available, but availability is separate from durability. Once I acknowledge a message, it must be durably accepted within the failure model. I do not need global ordering; I need meaningful ordering within a conversation or channel while unrelated conversations remain independently scalable. Durable history must converge across devices, while read position can be fast eventually consistent. With those requirements frozen, I would next quantify write throughput, fan-out delivery, bandwidth, storage growth, and connection capacity.”

What We Are Solving

Capacity estimation converts product assumptions into the order-of-magnitude workload the architecture must sustain. The objective is not to guess Slack’s real production numbers. We use explicit hypothetical assumptions so later decisions about partitioning, storage, Kafka, WebSocket gateways, fan-out, sharding, and failure capacity are quantitatively defensible.

By the end of this section we should understand message ingestion, average and peak traffic, operating headroom, bursts, message size, logical and physical storage, outbox write amplification, network ingress, fan-out, history reads, persistent connections, heartbeat traffic, reconnect bursts, and the arithmetic pressure at 10× and 100×.

Capacity dimensionQuestion

BandwidthHow many bytes per second move through the system?
StorageHow many bytes accumulate over time?
ConcurrencyHow many requests or connections are active simultaneously?
Fan-outHow much downstream work does one logical write create?
A messaging system does not have one capacity number. 500K messages/sec and 10M WebSocket connections are completely different capacity problems.

Write Throughput

The baseline inputs first establish daily volume and then average ingestion. There are 86,400 seconds in a day.

5,000,000,000 ÷ 86,400
≈ 57,870 messages/sec

Reusable formula

average operations/sec = users × operations/user/day ÷ 86,400

Average vs Peak vs Capacity Target

An average is not a provisioning target. Messaging traffic varies by work hours, geography, incidents, major events, and exceptionally active channels. Using an illustrative 5× peak factor gives 58K/sec × 5 ≈ 290K writes/sec. The factor is a planning assumption, not an industry standard.

The ≈500K/sec value is an initial write-path capacity target with headroom—not another estimate of expected traffic.

Why Headroom Matters

Headroom is not merely reserved for growth. It absorbs unexpected bursts, uneven partition distribution, rolling deployments, maintenance, retries, temporary downstream slowdown, forecasting error, and loss of instances or an availability zone.

Capacity Under Failure

Suppose the 500K/sec target is distributed evenly across three availability zones. Each zone contributes roughly 167K/sec. Losing one zone leaves approximately 333K/sec across the two survivors—above the 290K/sec modeled peak in this simplified calculation.

Healthy:  3 zones × ≈167K/sec = ≈500K/sec
1 AZ out: 2 zones × ≈167K/sec = ≈333K/sec
Modeled peak                         ≈290K/sec

Real deployments are not perfectly balanced, failover adds load, and operating at the exact saturation boundary is unsafe.

Capacity principle

Capacity planning should consider peak traffic after a failure, not only peak traffic when every component is healthy.

Global Peak vs Localized Hotspot

A global peak makes large parts of the system busy together—for example, traffic moving from 58K/sec average to 290K/sec during a busy period. A localized hotspot overloads one partition, channel, shard, tenant, or region even when aggregate utilization is comfortable.

Entire cluster utilization = 50%
but
one Kafka partition        = 100%+
Healthy global capacity does not imply healthy per-partition capacity.

The hot-partition architecture is analyzed—not solved here—in Section 6 — Scaling Deep Dives.

Message Size: What Are We Counting?

To convert message counts into bytes, use 1 KB average persisted/event payload as a working interview assumption. Files remain out of scope. The estimate covers message text, identifiers such as messageId, conversationId, and senderId, timestamp, ordering metadata, flags, and basic envelope overhead.

This is a round order-of-magnitude input—not an industry standard or a claim about Slack. For simple interview arithmetic, use decimal units: 1 KB ≈ 1,000 bytes, 1 TB ≈ 10¹² bytes, and 1 PB ≈ 10¹⁵ bytes.

Logical message size, database record size, Kafka wire size, and WebSocket wire size differ because of indexes, serialization, protocol headers, TLS, WAL, compression, and storage-engine metadata. Begin with application bytes, then layer on physical amplification.

When a capacity assumption is uncertain, use sensitivity analysis rather than pretending one estimate is precise.

Authoritative Message Storage

At the 1 KB working case, 5B messages/day × 1 KB ≈ 5 TB/day of logical history. Across one year, 5 TB × 365 ≈ 1,825 TB ≈ 1.825 PB before replication, indexes, metadata, backups, and storage-engine overhead.

This magnitude makes one unpartitioned database node implausible as the long-term message-history architecture. Storage partitioning is not premature optimization; it follows from the model. The final technology and shard key remain decisions for Section 3 — APIs & Data Model and Section 4 — High-Level Architecture.

Logical vs Physical Storage

Logical storage is the application data represented by messages. Physical storage includes replication, indexes, WAL, metadata, compaction, backups, and temporary copies. With replication factor 3:

5 TB/day logical × 3 ≈ 15 TB/day replicated
1.825 PB/year logical × 3 ≈ 5.475 PB/year replicated
Working implication

≈5.5 PB/year replicated message data before index, WAL, backup, and other overhead.

Retention, archive, tiering, compaction, and deletion may move data out of the hot tier; those policies are later decisions.

Write Amplification from Message + Outbox

The durable ACK contract from Section 1 means one accepted message creates at least one Message insert and one Outbox Event insert in the same transaction. At the 500K message-writes/sec capacity target, that is conceptually 500K message transactions/sec but at least 1M primary row inserts/sec, before indexes, WAL, replication, and metadata.

This is capacity math, not a claim that one relational database instance can sustain 500K ACID transactions/sec. It explains why the durable write workload may later need partitioning.

Outbox Byte Amplification

If an outbox row stores a full event roughly comparable to the 1 KB payload, logical inserts may approach 5 TB/day message data + ≈5 TB/day outbox data = ≈10 TB/day before replication and indexes.

The outbox is operational integration state, not permanent history. Processed records need not share message-history retention. Polling versus CDC such as Debezium is not decided here; Section 2 only records that each accepted message creates outbox write throughput and temporary storage volume. Transaction details continue in Section 5 — Critical End-to-End Flows.

Kafka Capacity Is Not Message-History Capacity

The Message Store owns long-lived authoritative conversation history. Kafka provides durable event transport and buffering for asynchronous consumers, normally with a different retention window. At 1 KB and the average 5B events/day, Kafka receives approximately 5 TB/day logical event volume, or about 15 TB/day with replication factor 3, before compression and broker overhead.

Ingestion Is Not Delivery

One stored message can create many delivery operations. A DM has very low fan-out; small channels generate tens of deliveries; large channels may generate thousands; and a very large online channel may create 100,000 or more.

delivery operations/sec

One overall average can conceal a heavy-tailed distribution. A defensible model segments DMs, small channels, medium channels, large channels, and extreme hot or celebrity channels. Exact delivery capacity requires the DM/channel mix, channel-size distribution, online-member percentage, and active sessions per recipient; we do not invent those percentages here.

Multi-Device Delivery Amplifies Fan-Out Further

A logical recipient may have desktop, browser, and mobile sessions active. The eventual relationship is closer to delivery pushes = messages × online recipients × active recipient sessions. Whether to push to every session or use another synchronization strategy is a later decision; this section records only the capacity implication.

History / Read Capacity

The system has at least four major traffic classes: message writes, real-time deliveries, history/synchronization reads, and connection/reconnection traffic. History reads include opening a conversation, fetching the newest page, backward pagination, reconnect catch-up, gap recovery, and multi-device synchronization.

history request QPS
= active users × history fetches/user/day ÷ 86,400 × peak factor

message records read/sec
= history request QPS × page size
Illustrative example

10K history requests/sec × 50 messages/page = 500K message records/sec before caching.

There is no universal Slack read/write ratio. If read behavior is missing, say: “I would model history reads separately using conversation opens, pagination frequency, page size, and reconnect behavior rather than assuming they equal the message-write rate.”

Heartbeat / Control Traffic

Persistent clients consume resources even without application messages. With 10M connections, one heartbeat per 30 seconds produces about 333K heartbeat events/sec; at 60 seconds it produces about 167K/sec. Ping and pong frames may increase control-frame volume.

10M ÷ 30 seconds ≈ 333K heartbeat events/sec
10M ÷ 60 seconds ≈ 167K heartbeat events/sec
Long-lived connections create capacity load even when application message traffic is low.

Reconnect Bursts

Because Section 1 promises reconnect recovery, we must quantify churn before designing recovery. A reconnect does more than open a TCP socket: it may perform TLS setup, authentication, session validation, connection-registry updates, read-state synchronization, and missed-message recovery.

reconnect attempts/sec
= connections forced to reconnect ÷ recovery window

10%: 1M ÷ 60 sec  ≈ 16.7K/sec
25%: 2.5M ÷ 30 sec ≈ 83K/sec
50%: 5M ÷ 60 sec  ≈ 83K/sec

A storm simultaneously loads gateways, authentication, session/cache state, the connection registry, history reads, and replay/delivery systems. Rate limiting, jitter, backoff, and recovery behavior belong in Section 7 — Consistency, Reliability & Failures.

What I Should Know · Little’s Law

For a stable system, average concurrency is approximately throughput multiplied by average time in the system: L = λW.

L is average in-flight work, λ is average throughput, and W is average time in the system.

500K writes/sec × 0.2 sec average latency
≈ 100K write operations in flight

This is illustrative. Little’s Law assumes a stable system and uses averages; do not substitute a p95 latency as though it were the mean.

Utilization and Queueing

Operating continuously near 100% utilization leaves little room for variance, retries, slowdown, or node failure. As arrival rate approaches service capacity, queues and tail latency become increasingly sensitive. If arrival rate exceeds capacity, backlog grows continuously.

Incoming = 50K/sec
Processing = 20K/sec
Backlog growth = 30K/sec

Capacity headroom protects throughput and tail latency. Detailed hot-partition and consumer-lag behavior remains in Section 6.

Capacity Conclusions That Drive Later Architecture

  1. The write path must scale horizontally.A 290K/sec modeled peak and 500K/sec target cannot depend on one application process.
  2. The Message Store must eventually be partitioned.Approximately 1.8 PB/year logical growth makes a single-node long-term store unrealistic.
  3. Outbox traffic is not free.Every accepted message creates additional durable write work.
  4. Kafka and message-history capacity are separate.Kafka transports and buffers events; the Message Store retains authoritative history.
  5. Fan-out may dominate ingestion.One channel write may create thousands or hundreds of thousands of deliveries.
  6. WebSocket capacity is independent from write QPS.Connections add memory, file descriptors, heartbeats, routing, and churn.
  7. Reconnects are a burst workload.Network or gateway failures add connection attempts and synchronization reads together.
  8. Global capacity can hide localized saturation.A partition may overload while aggregate cluster utilization remains healthy.
  9. Capacity must include failure headroom.A design that works only when every node and zone is healthy is not highly available.
  10. 10×/100× is not solved by adding servers blindly.Storage, partition skew, fan-out, connection routing, and regional boundaries scale differently.

One-Line Interview Answers

Why calculate average QPS if we provision for peak?
Average establishes the base workload; peak and burst factors determine provisioning and headroom.
290K/sec vs 500K/sec?
290K/sec is the modeled peak; 500K/sec is capacity chosen to leave operating and failure headroom.
Why not use 500K/sec for daily storage?
It is an instantaneous capacity ceiling, not the expected rate sustained for all 86,400 seconds.
Logical message-storage growth?
At 5B/day and 1 KB/message, roughly 5 TB/day or 1.8 PB/year before replication and overhead.
Why is physical storage larger?
Replicas, indexes, WAL, metadata, backups, and temporary operational data amplify logical data.
How does the outbox affect capacity?
Each message transaction also writes an outbox event, adding row and byte amplification.
Why size Kafka separately?
Kafka is a retained event transport/buffer; the Message Store owns long-lived authoritative history.
Why can’t write QPS determine delivery QPS?
Delivery depends on DM/channel mix, channel sizes, online recipients, and active sessions.
What is fan-out?
The amplification from one logical message into delivery work for many recipients.
Why can fan-out dominate ingestion?
One message may be stored once but pushed to thousands or hundreds of thousands of sessions.
Why isn’t 10M connections another QPS number?
Connections are long-lived state consuming sockets, memory, heartbeats, routing, and reconnect capacity.
Why do heartbeats matter?
Millions of connections generate hundreds of thousands of control events/sec without user messages.
Why model reconnect bursts?
A failure can produce tens of thousands of handshakes/sec plus authentication and recovery reads.
Why does headroom matter?
It absorbs bursts, retries, variance, maintenance, and failure capacity loss while protecting tail latency.
Why can one workload fail while the cluster looks healthy?
Aggregate capacity can hide a hot partition, shard, channel, or region past its own limit.
What does Little’s Law tell us?
In a stable system, average in-flight concurrency is throughput multiplied by average time in system.
What I Would Say in the Interview

“For scale, I’ll start with explicit planning assumptions rather than pretend I know Slack’s production numbers. I’ll use 50 million daily active users, 100 messages per user per day, and 10 million peak client connections.

That gives me 5 billion messages per day, or roughly 58 thousand message writes per second on average. With an illustrative 5× peak, that is about 290 thousand writes per second. I would initially size the write path toward roughly 500 thousand per second so there is room for bursts and failures rather than designing exactly to the predicted peak.

I also would not treat message QPS as the whole capacity model. With a 1 KB working message size, we are already looking at roughly 5 TB of new logical message history per day, around 1.8 PB per year before replication. A message also creates outbox work, so durable write amplification is greater than one row per message.

More importantly, ingestion and delivery are different workloads. A DM may generate one delivery, while one large-channel message may generate thousands or hundreds of thousands. I would model fan-out from channel-size distributions and online-recipient counts rather than one arbitrary average.

The 10 million WebSocket connections are another independent dimension. I need to size gateway count, per-connection memory, heartbeat traffic, churn, and reconnect bursts separately from write QPS.

Those numbers identify where later architecture needs horizontal scale: the write service, durable store, event processing, fan-out delivery, and gateway tier. They also show why aggregate capacity is insufficient—we must detect hot partitions and localized bottlenecks separately.”

Final Capacity Principles

Average is not peak. Peak is not provisioned capacity. Capacity target is not sustained daily volume.

Throughput, bandwidth, storage, and concurrency are different dimensions. Logical storage is not physical storage. Ingestion is not delivery. One logical user is not necessarily one connection.

Global spare capacity does not fix a localized hot partition. A highly available system needs enough capacity to survive failures—not only healthy-state traffic. At scale, model distributions and outliers, not only averages.

Kafka topics, partitions, consumers, and groups

Partitions belong to the topic. Assignments are calculated independently inside each consumer group. Different groups can read the same partition independently, with independent offsets.

An application instance is a running process, pod, or VM copy of the consumer application. One instance may create multiple Kafka consumers; one instance → one consumer is only the simple mental model.

Rule 01Partitions belong to topics.
Rule 02Assignments happen independently inside each consumer group.
Rule 03Different groups independently read the same partition.
Rule 04Within one group, one partition is assigned to one consumer at a time.

If a topic has five partitions and a group has six one-consumer instances, only five instances can own assignments at that moment; one remains without a partition until assignments change.

Decision so far

Order within a conversation—not globally

Global ordering across Slack would serialize unrelated traffic and damage scalability. The useful initial requirement is ordering within a logical conversation or channel.

Important lesson

Availability does not imply acceptable latency

A continuously growing backlog can make a technically available real-time service functionally degraded.

Adding consumers does not automatically solve one hot partition: within a consumer group, that partition is assigned to one consumer at a time. More consumers help when work is distributed across more partitions.
