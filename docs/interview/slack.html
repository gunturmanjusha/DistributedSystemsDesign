01

Requirements & Scope

Constrain the problem before selecting technologies

First pass · ≈65%
What I would say in the interview

“Slack is too large to design meaningfully in one session. I’ll focus on the core real-time messaging subsystem: direct and channel messages, online delivery, durable history, and recovery after a temporary disconnect. I’ll exclude calls, search, integrations, file internals, threads, reactions, and push notifications unless you want one brought back into scope.”

Questions to clarify

Establish the contract first

  • Are both direct and channel messages required?
  • Must acknowledged messages survive process or node failure?
  • What ordering guarantee is useful: global or per conversation?
  • How quickly should online delivery feel?
  • How should temporary disconnection behave?
Scope

Core subsystem

  • One-to-one and channel messaging
  • Users belonging to multiple channels
  • Near-real-time delivery to online users
  • Persistent conversation/channel history
  • Temporary disconnection and later recovery
Initially out of scope

Adjacent systems

  • Voice/video and full-text search
  • Bots and integrations
  • File-storage internals
  • Threads and reactions
  • Push-notification infrastructure

FUNCTIONAL

Capabilities

Send a DM, send to a channel, retrieve history, receive messages in real time, and recover missed messages.

NON-FUNCTIONAL

Qualities

Low latency, durability, high availability, horizontal scale, meaningful ordering, failure tolerance, and millions of long-lived connections.

MECHANISMS

Architecture choices

Kafka, cache, gateways, replication, load balancing, partitioning, and outbox are possible mechanisms—not requirements.

Interview takeawayDo not immediately say “Kafka” or “Redis” during requirements gathering. First establish the problem each mechanism needs to solve.

Critical End-to-End Flows

Durable write and publication intent

Write path partial · ≈50%
What I would say in the interview

“I will only acknowledge after authoritative persistence. To avoid the database/Kafka dual-write gap, the message and outbox event commit together. The outbox publisher can retry Kafka publication because intent is durable.”

Failure scenario
  1. User sends Hello.
  2. The API receives it.
  3. If the API returns success immediately, it has made a promise.
  4. The process crashes before persistence.
  5. The user was told the message was sent, but it no longer exists.
Current invariantIf the sender receives successful acknowledgement, the message has been durably accepted by the system.

06

Scaling Deep Dives

Connections, Kafka semantics, ordering, and the hot partition

Initial · ≈20%
What I would say in the interview

“Ten million concurrent users mean roughly ten million long-lived connections, so this is a connection-management problem as well as a request-throughput problem. For the event stream, I’ll initially key by conversation ID to preserve per-conversation partition order, but I’ll call out that a single huge channel can exceed one partition’s processing capacity. That conflict is unresolved.”

Deep dive

HTTP versus WebSocket

Traditional HTTP is primarily request/response. Polling forces clients to ask repeatedly whether new messages exist, wasting resources or increasing latency. A WebSocket begins with an HTTP handshake and becomes a long-lived bidirectional connection, allowing the backend to push events immediately.

Terminology

Kafka topics, partitions, consumers, and groups

Partitions belong to the topic. Assignments are calculated independently inside each consumer group. Different groups can read the same partition independently, with independent offsets.

An application instance is a running process, pod, or VM copy of the consumer application. One instance may create multiple Kafka consumers; one instance → one consumer is only the simple mental model.

Rule 01Partitions belong to topics.
Rule 02Assignments happen independently inside each consumer group.
Rule 03Different groups independently read the same partition.
Rule 04Within one group, one partition is assigned to one consumer at a time.

If a topic has five partitions and a group has six one-consumer instances, only five instances can own assignments at that moment; one remains without a partition until assignments change.

Decision so far

Order within a conversation—not globally

Global ordering across Slack would serialize unrelated traffic and damage scalability. The useful initial requirement is ordering within a logical conversation or channel.

Ordering where ordering matters;parallelism everywhere else.

Millions of logical conversations do not imply millions of Kafka partitions. Millions of conversation IDs hash across a manageable number of physical partitions, so many conversations share each partition. Consumer lag and end-to-end latency grow continuously until real-time messaging no longer feels real time. The infrastructure may still technically be available.

!

Important lesson

Availability does not imply acceptable latency

A continuously growing backlog can make a technically available real-time service functionally degraded.

Adding consumers does not automatically solve one hot partition: within a consumer group, that partition is assigned to one consumer at a time. More consumers help when work is distributed across more partitions.

Ordering pressureStrict conversation-wide ordering favors serialization.
VS
Throughput pressureExtreme throughput favors parallelism.

Distributing a hot conversation across partitions while retaining a logical sequence has been considered, but it has not been designed and is not presented as the solution.

Next design questionHow can a very hot channel scale beyond one partition’s processing capacity without destroying the ordering semantics users actually need?
